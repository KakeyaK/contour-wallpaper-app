# Contour Live Wallpaper

Android live wallpaper that draws contour lines over a gradient whose colours change
continuously throughout the day. Implementation of the `Contour Live Wallpaper` spec.

## Building the APK without Android Studio

1. Create a GitHub repository and push this entire folder (including `.github/`).
2. Every push triggers the **Build debug APK** workflow. Open the *Actions* tab, go into
   the run and download the `contour-wallpaper-debug` artifact (`app-debug.apk`).
3. Install it on the device (allow unknown sources) and apply it from the wallpaper
   picker or with the **Set as wallpaper** button inside the app.

Locally with the Android SDK: `./gradlew assembleDebug` (JDK 17).

### Building without the Android SDK (Ubuntu packages only)

`build-local.sh` compiles the same code without Gradle, using `aapt2`, `dx`, `apksigner` and
`zipalign` from the Ubuntu repositories, the API 23 `android.jar` and `kotlinc` from GitHub:

```
sudo apt install aapt android-sdk-platform-23 dalvik-exchange apksigner zipalign openjdk-17-jdk-headless
# kotlinc 2.1: https://github.com/JetBrains/kotlin/releases -> unzip into /opt/kotlinc
./build-local.sh          # -> build-local/contour-debug.apk
```

That is why the code only uses APIs available in API 23 (and the settings UI is built with
Views, without Compose or AndroidX).

## Assets

The PNGs in `app/src/main/assets/` are generated by `tools/generate_assets.py`
(seed 42, 34 contours, 5 octaves):

```
pip install numpy matplotlib
cd tools && python generate_assets.py  # -> tools/assets/*.png
cp tools/assets/*.png ../app/src/main/assets/
```

Changing `SEED` at the top of the script generates a different terrain. The APK then has to
be rebuilt — the contours are not generated on the device (that is out of the spec's scope).

**Fix applied to the script:** the altitude levels are now computed only once, on the
master field, and reused for both sets (`contour_levels`). Previously, each crop computed
its own from its own min/max — since the central strip has a different min/max than the
whole field, the contours on the outer screen landed at different altitudes from those on
the inner screen and the map jumped when unfolding (acceptance criterion 6).

| `ui/PreviewView.kt` | Preview using the same compositor as the service |
| `build-local.sh` | Build without the Android SDK (see above) |

## Interface

The app's interface is entirely in English (including the default anchor names: Dawn,
Morning, Midday, Afternoon, Dusk, Night), as are the code comments and file names.

## Single-colour mode

The anchor editor has two options: **One colour** and **All five**. In the first, the user
picks a base colour and all five colours are derived from it by a fixed rule
(`SimplePalette.derive`):

- the background becomes two versions of the base colour, darker at the top and lighter at
  the bottom, with a slight hue shift and less saturation at the bottom (which is what the
  sky actually does); if the base colour is very close to black or white, the whole pair
  slides inward into range, otherwise the gradient flattens;
- the lines go to the light side if the background is dark, and to the dark side otherwise;
- each altitude band has a **target contrast**: 2.3, 3.1 and 4.2. This is what solves the
  problem of lines clashing with the background — previously there was only a floor (the
  legibility lock), so nothing stopped a line from shooting up to 8 or 10 contrast;
- the line hues stay within a few degrees of the base colour (-12°, +6°, +18°), with the
  middle one desaturated, so the three bands separate without leaving the colour family.

The target is never below the legibility lock chosen in the settings, so the lock never has
to correct anything afterwards. The editor shows the five generated colours and each line's
contrast, so the rule is not a black box.

The seed is stored in the anchor (`seed` field in the JSON) only so the screen remembers
where the colours came from — the five colours are always stored as well, and drawing and
interpolation are unaffected. Editing any of the five by hand turns off simple mode for
that anchor. The default anchors ship without a seed, in **All five** mode, because their
colours are hand-picked and don't follow the rule.

## Solar mode (following sunrise and sunset)

Enabled under **Settings → Sunrise and sunset**. The clock time goes through a continuous
mapping before looking up the palette:

- the actual sunrise lands exactly on the **5:00** anchor;
- the actual sunset lands exactly on the **20:00** anchor;
- the actual day and night are stretched or compressed over those two segments.

In winter the bright middle of the palette shrinks and the night gets longer. The mapping is
continuous and monotonic, including across midnight, so there are no colour jumps.

While the mode is on, it **overrides the times set by the user**, and the screen makes this
explicit in three places: the notice at the top of the section, each anchor in the list
showing `05:00 → 06:14 today`, and a note inside the anchor editor. The preview also shows
both times (`clock → palette`) when the mode is in effect.

The calculation is NOAA's solar algorithm, pure arithmetic: no network, no GPS at draw
time. The settings screen reads the location **only once** (*Use my location* button,
optional `ACCESS_COARSE_LOCATION` permission) and stores latitude and longitude; the
`WallpaperService` just does the math on each redraw, with no battery cost. Users who prefer
can type in the coordinates and never grant the permission.

On days with no sunrise or sunset (midnight sun, polar night), or with no coordinates set,
the app automatically falls back to the normal clock.

The coordinates and solar mode are not part of the palette JSON (they are location
settings, not colour settings), and *Restore defaults* does not touch them.

## Changes to the default palette

The 17:00 and 20:00 anchors deviate from the spec's original table because the top of the
gradient looked garish filling the whole screen:

| Time | Field | Before | After |
|---|---|---|---|
| 17.0 | bgTop | `#F6D8A8` | `#C2B2AE` |
| 17.0 | bgBottom | `#E79A63` | `#DE9468` |
| 17.0 | line2 | `#C56B14` | `#A95C11` |
| 20.0 | bgTop | `#432A5C` | `#2E2140` |
| 20.0 | bgBottom | `#B5567A` | `#A85670` |
| 20.0 | line3 | `#2B1930` | `#190F1C` |

The 17:00 top became a cool warm-grey, which is what the sky actually does in the late
afternoon (cool at the top, warm at the horizon), and the 20:00 top became a deeper violet.
The two line colours changed along with them because, with the new backgrounds, they fell
below 2.1 contrast — the values in the table are already what the lock would produce,
keeping the rule that the default palette ships already locked.

This changes acceptance criterion 5: *Restore defaults* brings back these six anchors, not
the ones from the original table.

## Decisions the spec left open

- **Single colour** uses the *line 2* (middle) colour over `lines_*.png`.
- Scaling: fits to height and centres horizontally (as requested). If the launcher's
  parallax surface is wider than the scaled bitmap, the scale goes up so no empty edges
  are left.
- A new anchor is created with the current time and the colours interpolated for that
  moment.
- In solar mode the reference points are 5:00 and 20:00, the times of the default palette's
  "Dawn" and "Dusk". Editing the colours of those anchors works normally; moving their
  times changes the alignment with the sun.
- Exported JSON format: `{"version":1,"anchors":[...],"layerMode":"three","contrastTarget":2.1,"intervalMinutes":1}`.
  Import also accepts just the list of anchors.
